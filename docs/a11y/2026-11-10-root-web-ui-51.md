# Accessibility audit: `/` after web-ui task 51 (iPhone SE, Safari with the Bottom tab bar)

Date: 2026-11-10. Auditor: `a11y-auditor` (Playwright MCP, Chromium, touch emulation). Dev server at `http://localhost:3000/`.
Scope: the screens and components that task 51 changed, from `.kiro/workflow-output/status.json` and `plan.md`:
`lib/layout.ts` (`STACK_SHORT_QUERY`, `stackSuggestionRows`), `components/CommunicationScreen.tsx` (no suggestion row under 548px),
`components/MenuSheet.tsx` (new "Sentences" button), Req 24.6, 24.9, 25.1 and ADR-005.

This report lists what was checked and what was found. It does not state that the app is WCAG compliant or accessible.
Nothing outside `docs/a11y/` was edited. Screenshots are in `docs/a11y/screens/` (file names start with `task51-`).

## Findings

### 1. Text spacing pushes the action bar off screen (moderate, pre-existing)

- Criterion: WCAG 1.4.12 Text Spacing (line height 1.5, letter spacing 0.12em, word spacing 0.16em, paragraph spacing 2em). Accessibility rule 11 (no page scroll on touch) is also affected.
- Where: `.app--stack .shell-screen` (fixed-height one-screen shell), on every phone height, so task 51 did not cause it.
- Evidence (Playwright, style override `*{line-height:1.5!important;letter-spacing:.12em!important;word-spacing:.16em!important}` on a typed sentence):

  | Viewport | Page scroll before | Page scroll after | Action bar bottom after |
  |---|---|---|---|
  | 375x495 | 0 | 61px | 556px (screen is 495px) |
  | 375x549 | 0 | 71px | 620px |
  | 390x699 | 0 | 63px | 754px |
  | 402x654 | 0 | 60px | 706px |

  At 375x495 the sentence "Hello" also overflows its 48px line box (scrollHeight 60). Screenshot: `screens/task51-textspacing-375x495.png`. The Menu sheet buttons stay 343x56 with no clipping.
- Smallest fix: let `.app--stack .shell-screen` scroll inside itself (`overflow-y: auto`) with the action bar `position: sticky; bottom: 0`. Without spacing overrides nothing changes. Or record 1.4.12 next to 1.3.4 as a known exception in the About accessibility statement. This needs a product decision.

### 2. Alternatives are hidden below 548px (minor)

- Rule: Req 24.9 trade-off (ADR-005), not a WCAG failure.
- Where: the stack shell with no `.phone-sugg` row; the live region.
- Evidence: at 375x495 the section order is speak, pad, actions. The polite live region says only "Sentence: He", the same text as at 549px, so nothing tells a screen reader or sighted user that more sentences exist. The row's "Spell <keys>" and "Add X to my words" offers have no main-screen replacement; Spell this word is in Menu, Add to my words only through Menu > My words. A no-match word shows the placeholder "Xxxx" with the same screen at 375x495 (`screens/task51-nomatch-375x495.png`).
- Smallest fix: when the row is dropped and there is more than one sentence, add the count to the Menu sheet button label ("Sentences, 3") and to the live region text ("Sentence: He. 3 sentences in Menu"). Wording needs sign-off; do not add numbers about accuracy or speed.

### 3. The 548px threshold has no margin (minor)

- Rule: accessibility rule 1 (keys at least 72px); WCAG 1.4.4 (browser zoom gives fractional heights).
- Where: `packages/web/lib/layout.ts`, `STACK_SHORT_QUERY = '(max-height: 547px)'`.
- Evidence: measured minimum key heights at 375 wide: 548px gives 72.0 with the row, 549px gives 72.3, 547px gives 87.8 without the row. The query is false for 547.5px, so the row shows with a pad about 0.5px shorter than at 548 and keys of about 71.9px (calculated from the 548px layout, not measured; the MCP viewport takes whole pixels).
- Smallest fix: `(max-height: 547.98px)` so every height below 548 drops the row.

### 4. Same icon for Menu and Sentences (minor)

- Rule: design system, icons beside a word and distinct meaning.
- Where: `MenuSheet.tsx` line 56 and the action bar Menu button (`CommunicationScreen.tsx` line 853) both use `icon="menu"`.
- Evidence: `screens/task51-day-menu-375x495.png` shows the three-line icon on "Sentences". The word is present, so this is not a color-or-icon-only problem.
- Smallest fix: use the `check` icon the plan allowed as a fallback, or add a list icon in `Icon.tsx` in the same style.

### 5. Touch screens under 495px still scroll (minor)

- Rule: accessibility rule 11.
- Evidence: 360x400 touch: page scroll 84px, keys 72px, no suggestion row. The responsive suite and Req 25.1 start at 495px, so this is a documented floor. Keys cannot shrink below 72px.
- Smallest fix: none for task 51. If a shorter visible height matters (for example a split-screen Android window), measure it and add it to `responsive.mjs` before deciding.

### 6. One-line sentence card at 495px (minor, unchanged)

- Rule: accessibility rule 2 and design-system "SpeakBar": never truncate. Req 24.6 keeps one line under 680px.
- Evidence: after seven words at 375x495 the card shows one line; its text box has scrollHeight 194 and clientHeight 48 and stays on the newest line. The keypad stayed at y=88 (no movement) and the page did not scroll (`screens/task51-long-375x495.png`).
- Smallest fix: none for task 51. Show mode is the way to see the whole sentence.

## What I could not test

- Real iPhone SE, iPhone 17 Pro or any other phone and tablet, and Safari itself. These were Chromium touch emulations (WebKit through the e2e script only if you run `ENGINE=webkit`). The Bottom tab bar height (495px) was set by hand, not produced by Safari.
- Safe-area insets (`env(safe-area-inset-*)`): the MCP cannot set them, so the installed-app case on a phone with a home indicator is untested against the 548px rule.
- Screen readers (VoiceOver, TalkBack, NVDA): only the accessibility tree and the live-region text were read.
- Real switch hardware, or scan timing at 400 ms and 5 s. Scanning order was checked with the keyboard Space key only.
- Browser zoom at 200% on a phone, and fractional visible heights (finding 3 is calculated).
- `/welcome` (first run) and the Show, Phrases, My words and Settings sheets were not re-audited; task 51 did not change them. The existing `axe.mjs` run in `status.json` covers `/`, `/welcome`, `/about` and Settings.
- I did not re-run the e2e scripts; I read their results in `status.json` (responsive, axe, keyboard, switch all pass).
- The Next.js dev indicator (round badge, bottom left) overlaps the Menu button in every dev screenshot. It does not exist in a production build, so it is not counted as a finding.
